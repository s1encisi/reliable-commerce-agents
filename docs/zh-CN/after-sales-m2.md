## 本轮采用的规则

规则版本为 `returns-v1`，按原方案默认值实现，属于本地教学项目的业务设计。

| 条件 | 行为 |
| --- | --- |
| 身份与归属 | 使用认证上下文，仅访问当前用户的订单；他人订单与不存在的订单使用相同错误 |
| 状态 | 仅 `delivered` 可申请；已有退货记录时拒绝新申请 |
| 时间 | 使用有时区时间，接受 `delivered_at ≤ now ≤ delivered_at + 30×24 小时`；剩余天数仅用于显示 |
| 签收证据 | 缺失、空时间、未来时间、早于下单时间或不同签收时间相互矛盾时返回 `NEEDS_REVIEW` |
| 重复事件 | 相同签收时刻的重复记录不构成矛盾 |
| 订单选择 | 只有一个候选订单时可继续；多个候选或多个 UUID 时返回 `NEEDS_INPUT` |
| 原因与方式 | 原因去除首尾空格后须为 1–255 字符，与数据库列长一致；退款方式只接受已有两种值 |
| 审批 | `HITL_ENABLED=true` 或可信订单金额严格大于 `RETURN_HITL_THRESHOLD` 时需要审批；仅关闭 HITL 不豁免高金额门槛 |
| 审批绑定 | 保存主体、规范化参数散列、订单证据快照散列、政策版本及 24 小时有效期；等待期间发生变化时拒绝旧审批 |
| 结果 | 创建申请后才返回 `SUCCEEDED` 和 `return_id`；不声明退款已经到账 |

普通工具需要审批时返回 `status=pending_approval`、`request_id` 和消息。
REST 同样返回这些字段，但使用 HTTP 409 及字符串 `detail`：现有订单页面会把任何 2xx 当成“退货已创建”，
所以等待审批必须进入其提示分支，避免虚假的成功提示。其他拒绝仍保留原有 HTTP 错误状态与字符串 `detail`，
新增 `outcome`、`error_code` 和 `policy_version` 位于响应顶层。审批通过但执行失败时保留原有 `approved` 状态，
通过 `execution_result.success=false` 和业务结果说明原因，不会记录为 `executed`。
这样保留管理员页面的状态兼容性，同时区分授权决定和实际执行。

## 执行链路

```mermaid
flowchart LR
    A[资格判定] --> B[绑定动作并等待审批]
    B --> C[锁定订单与签收证据]
    C --> D[重读规则及当前时间]
    D --> E[同一事务写申请和订单状态]
    E --> F[提交后返回申请标识]
```

工作流的审批节点已移到创建退货之前。检查点保存原用户、原因和审批绑定；
新工作流实例恢复时，先重新验证，再首次提交申请。拒绝审批时没有退货写入。
并发恢复由数据库原子领取审批记录，只有一个请求进入恢复执行。

提交事务按固定顺序锁定订单及既有状态历史，再读取时钟，防止等待行锁时跨过期限却继续提交。
申请记录、订单状态和退货历史在同一事务中写入；其中任一步失败均回滚。
查询不到签收时间时不会用下单时间或当前时间补造证据。

## 升级兼容性和后续范围

没有新增数据库表或修改既有列类型，已有数据不需要清空重建。
较长原因现在在写入前拒绝。旧的待审批记录和检查点若缺少新政策绑定，不会被当成新政策下的授权；
需要重新发起申请并取得有效审批。既有退货仍保持原订单生命周期字段。

退货工具仅缓存确认成功的结果，待核实、待审批和拒绝结果不会永久冻结后续检查。
其他工具保留原幂等缓存键。现阶段仍未实现完整业务操作记录：进程中断可能留下
`processing` 审批，业务提交与幂等缓存写入之间仍有窗口。这些属于 M3，不能把本轮事务与行锁
测试称为跨进程“恰好一次”保证。

M3 将实现稳定 `operation_id`、原子操作结果与未知提交结果核实；M4 再冻结版本、进行故障对照和消融。
真实模型实验仍需单独确定服务及费用上限。
