# 测试与评估：让分数对应真实结果

[上游评估框架](../../agents/python/evals/README.md) · [售后技术方案](after-sales-reliability-plan.md)

## 四种证据分别证明什么

| 层级 | 输入与环境 | 能证明 | 不能直接证明 |
|---|---|---|---|
| 单元测试 | 固定参数、内存数据或替身 | 规则函数、校验和评分逻辑 | 真实服务和模型表现 |
| 模型回放 | 已录制响应、真实框架循环 | 固定轨迹的回归与连接关系 | 新问题泛化、真实延迟与费用 |
| 数据库 / API 集成测试 | 专用 PostgreSQL、真实入口、受控故障 | 事务、权限、并发和状态恢复 | 所有未知模型行为 |
| 真实模型评估 | 固定模型设置、隔离场景、重复运行 | 模型与系统协同的任务表现 | 整个生产分布或绝对安全 |

不要用回放的瞬时响应报告在线 p95，也不要把缺失 usage 记为零成本。

## 当前实现与历史文档

当前 [evals/harness.py](../../agents/python/evals/harness.py) 提供 ProductionRunner，[db_groundedness.py](../../agents/python/evals/scorers/db_groundedness.py) 读取核验报告。部分上游旧说明仍把 groundedness 描述为“至少调用一个工具”；阅读时应核对现行实现。

第 26 章的教学评分器使用子串匹配，judge_response_stub 使用启发式，并非真实 LLM judge。回答包含数字不保证数字语义正确，拒绝措辞也不保证没有越权动作。

## 售后任务必须有最终状态断言

一个案例至少包含：

    case_id
    initial_database_state
    user_request
    fault_schedule
    allowed_actions
    expected_business_state
    expected_response_class

同时核对返回文本、工具名与参数、审批记录、操作状态、returns / orders 等数据库记录。按可信数据判断业务事实，不把模型的“我已经完成”当作事实来源。

## 评价指标

- 可执行任务完成率与正常请求误拒率。
- 可恢复故障后的完成率。
- 不允许请求的违规执行次数。
- 相同 operation_id 导致的重复业务写入次数。
- 结果未知后的核实成功率。
- 端到端耗时、失败和超时比例、p50/p95、吞吐与并发级别。
- 模型调用、工具调用、重试、token、费用、缓存命中，以及费用缺失比例。

安全结束和业务完成分开统计，避免“全部拒绝”获得最高成功率。故障请求不能从延迟报告中悄悄删除。

## 实验边界

先划分开发与验收场景，再修改规则、提示词和阈值。同一订单的换说法、同一故障模板的近似副本按场景族归组，避免分到两侧。

每个试验恢复数据库初始状态，隔离会话、操作记录、幂等键、Redis 缓存和工作流检查点。基线和改进版使用相同模型、采样设置、工具描述及故障种子；变化作为显式实验因素记录。

对正常与异常任务分别报告样本量和不确定性。少量重复的尾延迟只作探索性结果；零次违规必须带测试次数，不能外推为零风险。

## 现有模式对比的限制

[上游编排对比](../orchestration-benchmark.md)记录的是历史实验：4 个问题、每种模式每题 2 次。部分工作流没有模型调用，退货工作流只走到拒绝资格分支；部分模式缺少 token 与费用数据。这些历史数据不属于本分支的新实验，也不足以支持跨模式的全面性能排名。
