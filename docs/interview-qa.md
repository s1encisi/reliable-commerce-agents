# 面试问答：Reliable Commerce Agents

回答基于本分支已实现与已验证的内容。项目采用开源基线和 AI 辅助开发；请按本人实际参与和理解的范围表述，不能把上游能力、未运行实验或预期业务收益当成个人成果。

## 先准备两段介绍

**30 秒版**

这个项目是一个电商多智能体平台，我围绕售后退货做了可靠性改造。重点是让工具调用遵守统一规则，在人工审批后才执行，并且在网络断开或进程中断后能核实申请是否已经成功。我用真实 PostgreSQL、进程退出和 TCP 断连测试验证了这条链路，并提供了可重复运行的本地演示。

**两分钟版**

项目基于 Microsoft Agent Framework 的开源电商平台，上游已经提供了多个智能体、工具、前端和检查点。我选择退货申请作为切入点，因为它涉及权限、期限、人工审批和业务写入，不能只看模型是否说了“成功”。

我先复现了缺少签收证据仍可退、不同入口执行不同规则等问题，再统一政策和提交服务，把审批移到副作用之前。随后加入由客户端持有的操作标识，将申请和执行回执放在同一个事务中。遇到提交确认不明时，系统先查回执，无法确认就明确返回未知。

验证包括真实数据库、并发、子进程在提交前后退出，以及代理丢弃 COMMIT 回执。还有固定场景的版本对照与消融。结果支持这条本地退货链路的工程改进，但不能据此宣称真实模型准确率、生产容量或跨支付系统的恰好一次。

## HR 常问

### 1. 这个项目解决什么实际问题？

解决“系统会调用工具，但执行结果不可信”的问题。例如用户断网后重试，系统可能无法判断申请是否已经创建；审批等待期间订单也可能过期。改造让不同入口遵守同一规则，并且用数据库证据回答成功、拒绝、等待或未知。

### 2. 为什么选这个项目？

它有可解释的业务闭环和可观测的副作用。可以直接检查订单、审批、退货记录和操作回执，而不是只评价一段聊天文字。这适合展示如何把智能体接入实际业务约束。

### 3. 你个人做了什么，上游做了什么？

上游提供六智能体、A2A、编排、商城前端、认证、检索和初步防护。本分支增加统一退货政策、审批绑定、持久操作记录、恢复与结果确认，以及相应测试、对照和演示。介绍时应指出具体文件和测试，不能把整个平台说成个人从零完成。

### 4. 创新点是什么？

是业务执行层的改进：把分散规则收敛到可信服务，把审批与具体意图绑定，把业务效果和可查询回执原子保存，再用故障实验证明差异。事务、幂等和锁本身都是成熟技术，项目价值在于识别缺口、正确组合并验证。

### 5. 有什么量化结果？

评估采用 22 类固定场景、每类 3 次重复，并保留逐案例结果。当前实现与冻结基线、三个消融版本的结果见 [验证记录](verification.md)。可以引用该记录的计数，但不能将“66 项条件检查通过”说成“生产成功率 100%”。重复运行不是独立真实用户样本。

### 6. 上线了吗？业务收益是多少？

目前是本地可运行的工程原型和合成数据演示，没有真实商家上线或真实退款。已证明的是受控条件下的规则一致性和恢复行为；减少投诉、重复申请或人工核实成本属于潜在收益，需要上线后测量。

### 7. 最困难的问题是什么？

最容易误判的是“数据库已经提交，但客户端没收到回复”。直接重试可能重复执行，直接报失败也可能与数据库事实不符。我将操作结果和业务写入放在同一事务，并通过新连接核实结果，验证时真的丢弃了 COMMIT 回执。

### 8. 使用 AI 辅助后，你的价值体现在哪里？

应该说明自己实际做过的需求拆解、规则取舍、代码审查、实验设计和复验。能够解释为什么旧方案会失败、每个锁和状态解决什么问题、证据有哪些限制，比声称手写了全部代码更可信。不能解释的部分应先阅读和复现。

## 技术面试追问

### 9. 为什么还需要智能体，固定工作流不够吗？

自然语言理解、跨域工具选择和信息整理由智能体承担；高风险写入由固定服务校验。项目既保留自由工具调用，也保留可解释的 MAF 工作流。没有在不同任务之间直接比较分数，因而没有证明多智能体必然优于单智能体。

### 10. 如何处理提示词注入或模型试图跳过规则？

身份从认证上下文取得，操作标识来自可信请求边界，模型只提供受校验的业务参数。所有实际写入都进入统一服务，重新检查归属、状态、期限和审批。此设计限制越权写入；它不等于已经完成所有提示词攻击或模型行为的实测。

### 11. 为什么普通幂等缓存不够？

业务提交与缓存结果分开写，会出现“申请已创建、缓存仍在处理中”的窗口。本实现先持久化操作意图，再将退货申请、订单状态和成功回执放在同一事务。重试读取持久回执，因此不依赖某个进程的内存。

### 12. operation_id 从哪里来？

浏览器在发请求前生成并保存 UUID，相同意图重试复用它；后端按用户隔离。参数散列用于检测同标识不同参数。旧调用没有显式标识时采用稳定派生标识。标识和散列都不是身份凭据，权限仍依赖认证与订单归属。

### 13. 如果数据库返回 READY，就能认为没提交吗？

不能直接读一个旧快照就下结论。另一个事务可能正在提交。确认查询会等待操作记录上的写锁；等不到就返回 UNKNOWN，避免把在途写入误判成回滚。

### 14. 如何保证并发不会产生两份退货？

同一操作先锁操作记录，不同操作再竞争同一订单行；数据库唯一索引限制每个订单一份退货。成功重放返回原回执。这里的保证范围是受本服务控制、同一个 PostgreSQL 中的退货申请，不包含外部支付和物流。

### 15. 审批之后为什么还要再校验？

等待期间订单可能过期、证据可能被修正、金额或参数也可能变化。批准绑定的是当时的明确意图，并不自动豁免业务政策。执行前检查当前数据和绑定；不匹配时要求新的明确意图或审批。

### 16. 进程在审批恢复中途退出怎么办？

批准/拒绝决定先持久化。恢复使用 session advisory lock 减少重复工作；连接消失后可由下一请求继续，但不能改变原决定。最终业务防重仍依赖操作记录事务和唯一约束，不能仅靠“超时后旧任务应该已经停止”。

### 17. 哪些故障能重试，哪些不能？

明确没有提交的暂时数据库失败可在预算内重试。业务拒绝不重试相同意图。COMMIT 已发出后的异常先核实，无法确认则保持 UNKNOWN。准备和执行有明确尝试上限，共享应用 deadline，避免多层重试叠乘。

### 18. 用户取消是否意味着一定没有写入？

不意味着。取消阻止新增尝试，但在途提交可能已经完成。界面应保留操作标识并查询最终结果，不声明已经撤销远端事务。

### 19. 测试有没有只 mock 出理想结果？

数据库测试使用真实 PostgreSQL。进程故障通过子进程退出触发，COMMIT 确认丢失通过 TCP 代理触发，浏览器响应丢失也先把请求交给真实服务再丢弃响应。纯规则测试使用显式时钟。没有运行的真实模型测试明确跳过。

### 20. 对照和消融如何避免夸大？

基线源代码冻结并记录散列，每个 trial 清理独立测试数据，同一场景比较相同业务目标。消融只在独立评估进程中关闭一个机制。报告故障是否真正触发、数据库效果和明确分母；本地服务 p95 不当成生产 SLA，合成回归集不当成模型保留集。

### 21. 老数据库怎么升级？

提供可重复执行的增量迁移，同时保留新库初始化路径。新增唯一约束前检查已有重复数据，发现冲突就停止，不自动删除记录。旧审批缺少必要绑定时不自动赋予新政策下的权限。

### 22. 如果接入真正退款系统，你会怎么改？

使用支付方幂等键和结果查询，必要时增加 outbox、对账及人工处理队列。本地事务不能回滚已经发生的外部支付。需要把外部结果未知、补偿和权限审计单独设计并测试。

### 23. 下一步最值得做什么？

先为真实模型准备冻结的开发/保留场景与费用上限，再验证自然语言澄清、工具选择和结果表述。业务侧可增加人工核实流程、细化订单售后生命周期，再考虑外部支付或物流。不能为了展示更多框架而放弃对同一业务目标的可比验证。
