# 项目讲解与贡献说明

## 30 秒开场

这是一个基于开源电商多智能体平台改造的可靠 Agent 项目，重点处理退货申请中的审批、重复提交与中断恢复。模型负责理解和编排，可信服务负责身份与规则，数据库回执负责确认实际结果。另有只读任务工作台，用结构化条件和真实工具证据验收步骤，并把尚未核实的自然语言目标交给用户确认。

## 两分钟结构

1. 业务问题：模型说成功、HTTP成功、数据库提交分别意味着什么。
2. 项目来源与职责：说明上游平台基础，以及自己实际参与的需求、设计取舍、代码审阅、验证和讲解。
3. 请求链：页面→协调器→工具/工作流→可信服务→事务与回执。
4. 核心案例：COMMIT后响应丢失，为什么先查同一操作而不是重发。
5. 证据：展示与当前代码匹配的测试/评估，解释数据来源和适用范围。
6. 演进：任务验收、约束修订、外部履约模拟；不把未接入的真实支付或模型质量写成成果。

## 五个可深入阅读的切口

| 追问 | 代码与证据 |
|---|---|
| 为什么不能只用幂等缓存？ | `shared/after_sales/service.py` 与 `operations.py`：业务写入和回执同事务；故障测试与售后评估 |
| 客户确认与管理员授权有什么不同？ | `orchestrator/routes/orchestration.py`、`shared/hitl.py`；跨入口权限回归 |

## 简历技术表述模板

以下是项目能力描述。写入个人简历前，须以实际参与情况确定“设计”“负责”等动词，并亲自核对最新验证结果。

- 基于 MAF、FastAPI 与 PostgreSQL 改造电商售后链路，统一多入口业务规则和管理员审批，使用操作标识、行锁、唯一约束及原子回执支持重复请求与中断恢复。
- 为只读任务增加结构化条件和实体验收，将未完整核验的自然语言目标转为人工复核，结合 revision、持久状态和会话锁处理规划及执行中断。
- 建立隔离数据库故障实验、中文检索评测及浏览器演示，记录实际版本、源码散列、失败案例和结果范围。

如需写数字，使用实际报告中的日期、版本、场景数量与结果，不把历史 66/66 当作当前模型准确率。无模型的服务微基准与真实模型任务质量必须分开写。

## AI 辅助开发如何说明

项目基于开源基础，不能把上游所有能力算作个人从零开发。本轮代码实现、测试执行、静态审查和部分材料由 AI 工具辅助完成。人的责任应以真实活动记录说明，不以是否逐行手打代码判断。

面试前为每个准备讲述的改造核实：

- 我为什么接受这个需求，放弃了什么替代方案？
- 我能否在不询问 AI 的情况下解释关键函数、SQL、状态转换和失败条件？
- 哪个失败用例在修复前会失败，修复后如何证明正确？
- 哪些是工具提出并实现的，哪些经过我亲自审阅、复现或调整？

尚未由本人完成的审阅或复现，不能写成既有个人工作。建议从一个审批用例、一个提交确认不明用例和一个任务错误完成用例开始亲自复验。

## 演示路径

按[本地演示指南](portfolio-demo.md)完成客户申请→管理员核对并批准→客户查询同一操作→缺证据或超期案例→故障评估证据。

再打开[任务工作台](task-workspace.md)，使用明确标注的离线固定示例，展示真实数据库工具、步骤证据及刷新恢复。模型计划中的目标和文字要求须人工确认；固定示例不能用来声称实时模型推理质量。

[外部履约模拟](fulfillment-simulation.md)用于深入解释跨系统失败与对账，默认关闭，不连接支付或真实物流。
